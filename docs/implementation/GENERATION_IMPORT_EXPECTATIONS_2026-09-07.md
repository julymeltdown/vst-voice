# Generated-candidate import expectations

Status: repository admission component implemented; durable resumable jobs remain incomplete.

## Recognition after producer publication

Guarded imports now store `generationExpectationSha256`, the SHA-256 of the canonical expectation JSON, in their procedural lineage in the same producer transaction as the take. Manual/legacy lineage retains its original six fields; guarded lineage has exactly those six plus this validated digest. Older six-field records remain readable but are not retroactively treated as generated-request proof. Readers that only understand six-field lineage cannot read this new guarded extension.

`findCollectedGeneration(expectation)` is read-only. It recovers and verifies durable producer state/assets, matches the exact original expectation digest and target, resolves unique strict candidate lineage and checks recipe/output identity and dimensions. It returns no result if the take is absent, rejects a colliding take without matching proof, or reports the current durable generation, raw digest, take state and whether the take remains assigned.

`import-generated` consults that method before attempting a new import. A proven retry returns `result: AlreadyCollected` without a save, new take, reassignment or review reset. A fresh successful import returns `result: Collected`. Manual boundary edits do not invalidate the historical collection record; a later retake yields `active: false` and the older take's current Retake state rather than resurrecting it. Historical recognition does not require disposable staged metadata/WAV/recipe files and does not claim to verify newly supplied staging paths. The original expectation and its retained digest are still required.

This recognizes committed repository history; it is not an authenticated external signature. The canonical importer still rejects stale requests that have not previously committed. Concurrent changes may require another read/retry; no context is silently refreshed. Batch/native orchestration and the other U21 acceptance requirements remain open.

## Durable expectation files

`saveGenerationImportExpectation(path, expectation)` validates and atomically publishes a new file, refusing replacement, then returns its SHA-256. `loadGenerationImportExpectation(path, expectedSha256)` requires the digest retained by the owning job, reads at most 16 KiB and verifies those exact bytes before parsing. A digest match alone is insufficient: unsupported versions, missing/extra fields, control characters, invalid hashes, out-of-range dimensions and overflowing numeric representations reject. Capture and guarded import use the same serialization validation contract.

The v1 JSON object has exactly 15 fields: `formatId` (`com.project-seam.generation-import-expectation`), `schemaVersion` (1), `projectStateSha256`, `takeId`, `promptId`, `coverageKey`, `supersedesTakeId`, `pitchLayer`, `recipeId`, `recipeVersion`, `recipeHash`, `style`, `renderContentHash`, `sampleRate`, and `frameCount`. Text is bounded to 256 bytes with no ASCII controls; only the superseded-take identifier may be empty. Hashes are 64 lowercase hexadecimal characters. MIDI is 0–127, rate 8–384 kHz and frame count 1–32 Mi. Parser bounds are depth 2, 32 nodes and 15 collection entries. Integer ranges are checked before narrowing.

Reloaded expectations feed the same canonical import checks; a restart must not replace them with newly captured state. These files are not signed and do not authenticate their containing job. The future durable job envelope still needs to retain the original expectation digest, score/recipe request and job identity together, and verify staged results before retry/publication. An expectation file alone does not implement restart/resume.

`captureGenerationImportExpectation` captures a validated initialized producer model's canonical state hash together with the intended take/prompt/coverage/pitch/superseded-take target, verified recipe identity, requested style, render content hash, sample rate and exact frame count. The selected assignment must match the request. The state hash covers generation, inventory, assignments, source strategy, manual metadata and other serialized producer state, including unsaved model changes.

Generation workers must retain the original captured value. At publication, pass it to `importProceduralCandidate` through its optional expectation argument. Before candidate IO, the repository checks the current in-memory producer state, target and recipe against the expectation. After strict candidate loading, it checks style, render identity and exact dimensions against the same request. Rejections at those checks do not import an asset or change assignments. The normal canonical import then applies its existing writer-locked durable-generation check; a concurrent save cannot be bypassed by an old in-memory model. Later publication failures may retain an unassigned content-addressed asset, as in existing import behavior.

The expectation is trusted caller data for staleness/integrity checking, not a cryptographic authorization token, signature or proof of source rights. The future durable job layer must serialize and bind it to the original request; it must not silently refresh the expectation when collecting an old worker result. Recapturing against a changed workspace means explicitly submitting a new request.

Manual candidate import remains available without a generation expectation. CLI `import-generated WORKSPACE METADATA WAV RECIPE EXPECTATION SHA256 OPERATOR UTC` loads retained expectations and enforces guarded collection through the same repository. It derives target fields from the file and never recaptures state. Its POSIX executable test verifies stale/wrong-digest rejection, current-request success and read-only repeated-call recognition without state changes. CLI/native manual import remains separate. Frozen request packages and worker reuse are documented in `GENERATION_JOB_PACKAGE_2026-09-07.md`; native/batch orchestration and broader interruption/acceptance qualification are still required for U21.

Tests exercise wrong output identity/duration/style/target, unsaved assignment changes, changes saved to a new durable generation, unchanged producer/assets after early rejection, and successful canonical import after explicitly capturing a new request. The imported material remains unapproved MarkerReview material and continues through recovery/manual editing tests. See the execution ledger for build/test evidence.
