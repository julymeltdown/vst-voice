# SEAM 개발 지연의 원인과 방향 재판단

작성일: 2026-10-10 · 목적: 개발을 재개하기 전에 사용자가 제품을 직접 보고 방향을 결정할 수 있도록 원인을 진단한다.

분석 기준: `master`의 `ecb031680de84cc987ee2153b069269f2eeb8d73`. 먼저 `git fetch origin`, `git pull --ff-only --no-rebase`를 실행했고, 로컬 HEAD·origin/master·실제 원격 master의 일치를 확인했다. 이 문서는 새 구현 계획이나 완료 판정을 승인하지 않는다.

## 1. 판단

**근본적인 문제가 있다. 가장 강하게 드러난 문제는 코드 전체가 잘못됐다는 것이 아니라, 제품의 핵심 불확실성을 줄이는 일보다 구현과 검증 체계를 정교하게 만드는 일이 계속 다음 작업으로 선택되는 개발 방식이다.**

SEAM은 많은 기능과 실제 실행 경로를 갖췄다. 그러나 “내가 만든 목소리로 낯선 가사를 부르게 하고, 편집해서, 다시 열고, 만족할 만한 노래로 내보낼 수 있는가”에 대한 확정된 답은 그에 비해 부족하다. 이 상태에서 설치 신원, 증거 형식, 검증기, 검증기의 실패 처리까지 계속 개선하면 기술적으로는 전진하면서도 사용자가 체감하는 완성은 멀게 느껴질 수밖에 없다.

**검증량과 코드의 결합도도 비용을 만든다. 다만 그것만으로 지연 전체를 설명할 근거는 없다.** 현재 증거는 전면 재작성보다 작업 선택과 피드백 순서를 먼저 바꿔야 한다는 판단을 지지한다. 음질·발음·목소리 정체성의 가능성은 아직 별도의 실험으로 판정해야 한다. 듣지 않고 “합성 방식이 틀렸다”거나 “기술적으로 거의 완성됐다”고 단정할 수 없다.

| 질문 | 판단 | 근거의 강도와 한계 |
|---|---|---|
| 구조적인 문제인가? | 작업 운영 구조에는 문제가 있다. 코드에도 변경 비용이 큰 경계가 있다. | 반복된 기존 진단, 최근 커밋, 실제 의존 관계로 확인. 전체 아키텍처 실패는 입증되지 않았다. |
| 검증할 게 많아서인가? | 실제 원인 중 하나다. 특히 여러 빌드 구성과 공유 머신 대기가 비용을 늘린다. | 두 작업의 시간 기록으로 일부를 계량했다. 전체 개발 시간에서 차지하는 비율은 모른다. |
| 틀리면 안 되기 때문인가? | 데이터 보존·동시성·자원 신원에는 맞다. 모든 탐색 작업에 같은 엄격함을 적용할 이유는 없다. | 제품 안전성 확인과 음악적 가능성 탐색의 목적이 다르다. |
| 본질적으로 불가능한 프로젝트인가? | 현재 증거로는 그렇게 판단할 수 없다. 핵심 음악적 타당성도 아직 충분히 확정되지 않았다. | 실제 연결된 렌더·편집·저장·출력 테스트가 있다. 그것이 원하는 음질을 보장하지는 않는다. |
| 지금 무엇부터 해야 하나? | 사용자가 짧은 실제 노래 작업을 해 보고, 가장 큰 실패 하나를 다음 작업으로 지정해야 한다. | 새 종합 계획을 늘리는 것보다 미해결 제품 질문에 직접 답한다. |

## 2. 이번에 확인한 사실과 확인하지 않은 것

기준 시점의 추적 경로 **3,022개는 모두 존재**한다. 따라서 현재 master의 추적 파일이 대량 누락되어 개발이 헛돌고 있다는 증거는 없다. 이는 외부 음원·학습 자료·승인된 리소스까지 완비됐다는 뜻이 아니며, 모든 보존 브랜치의 동작이 통합됐다는 판정도 아니다.

현재 정식 장부는 다음 상태다.

| 항목 | 실제 기록 | 해석 |
|---|---|---|
| Usable Alpha | 20개 중 PASS 0개, 모두 `NOT_RUN`, gate `BLOCKED` | 정식 실제 사용 증거가 등록되지 않았다. 20개 기능이 전부 없다는 뜻은 아니다. |
| External Beta | `BLOCKED`, evidence 0개 | 정식 Beta 승인을 뒷받침하는 기록이 없다. |
| 전체 계약 | 요구사항 20개, 작업 패키지 18개, 사례 83개, `evidenceStatus=NOT_RUN` | 정의된 범위의 크기다. 통과한 테스트 수가 아니다. |
| 평가·리소스 | 평가 프로필과 리소스 매트릭스 `UNRESOLVED`, `releasedResources=[]` | 최종 평가 기준·출시 리소스 등록이 끝나지 않았다. 로컬 실험 리소스가 전혀 없다는 뜻은 아니다. |
| 최근 활동 | 10월 8일 00:00 KST 이후 first-parent 커밋 53개 | 활동량은 크다. 기능 53개 완료나 투입 시간의 척도로 사용할 수 없다. |

이 숫자로 새로운 전체 진행률을 만들지는 않았다. 예전 약 54%는 임의 가중치를 둔 분류 지수였다. 현재도 전체 소요 작업량과 난이도가 검증된 분모가 없으므로 정확한 완료율을 말할 수 없다. **정식 Alpha 0/20도 전체 구현률 0%로 바꿔 읽으면 안 된다.** [S1], [S2], [S3]

이번에는 코드, Git 이력, 기존 실행 기록과 리뷰를 조사했다. 새 빌드, 제품 테스트, 실제 UI 조작, 청취, DAW·Windows·접근성·서명 검증은 하지 않았다. 이전 실행 기록은 해당 소스와 조건의 증거로만 사용했다. 현재 장부가 포착하지 못한 과거 개인 사용이나 청취가 있었을 가능성도 배제하지 않는다.

## 3. 가장 큰 문제: 이미 알고 있던 위험이 작업 순서를 통제하지 못했다

이 문제는 이번에 처음 발견된 것이 아니다.

- **9월 9일:** 실제 목소리 품질을 모르는 동안 계약과 테스트용 자료만 늘리면 가장 중요한 실패를 마지막에 발견하게 된다는 경고가 있었다.
- **9월 15일:** 구현 불확실성은 줄었지만 음악적 불확실성은 남아 있다는 공동 리뷰가 있었다. 새 기능보다 먼저 직접 청취 자료를 만들고, 청취·창작 결과가 다음 음향 수정을 정하도록 제안했다.
- **10월 8일 계획:** 전체 M0 완료를 기다리지 말고 기존 macOS 사용 흐름을 실행하고, 관찰된 창작 방해 결함을 다음 작업으로 고르도록 명시했다.
- **10월 9~10일 기록:** packet 003의 정식 양성 경로와 청취는 계속 열려 있고, 뒤따른 작업 상당수는 설치 신원 연결, 자원 승인 경계, 검증 신뢰성에 집중됐다. [S4], [S5], [S6], [S7]

따라서 “계획이 없어서 느리다”는 설명은 맞지 않는다. 계획은 이미 좋은 우선순위를 여러 번 제시했다. **실행 중 눈앞에 나타난 검증·정합성 문제가 다음 일을 계속 결정했고, 핵심 제품 질문으로 돌아오게 하는 중단 기준이 약했다는 것이 더 설득력 있는 진단이다.**

예를 들어 현재 U45 경로는 프로젝트 참조 확인 → 설치된 자원과 연결 → 저장된 설치 핀 대조 → 런타임 승인 → 렌더 소스 대조 → 확인한 프로젝트 보존 → 실제 출력 관찰로 세분화됐다. 각 경계는 실제 의미가 있다. 하지만 이 연속 작업은 상당 부분 “어떤 입력으로 실행했는지 신뢰할 수 있게 증명하기”를 개선한다. 그 자체로 “그 목소리로 노래하고 싶은가”를 판정하지 않는다. [S8], [S9]

현재 리드 에이전트인 나도 이 편향에 책임이 있다. 실제 결함을 고치고 검증 범위를 정직하게 기록한 것은 필요했지만, 계속 수행 가능한 기술 작업이 있다는 이유로 그 작업이 제품의 최우선 과제라고 취급한 것은 잘못된 선택이었다. 외부 입력을 기다리는 동안 독립 작업을 계속하라는 지침도, 어떤 독립 작업이 가장 가치 있는지 판단할 책임을 없애지 않는다.

## 4. 범위가 한 개의 앱보다 훨씬 크다

현재 목표에는 다음 서로 다른 개발·연구·운영 과제가 함께 들어 있다.

1. 노트·가사·발음·표현을 편집하고 저장·복구·출력하는 네이티브 음악 편집기.
2. 녹음 또는 생성 자료를 편집·검수·버전 관리·설치하는 보이스뱅크 제작 도구.
3. 원본 녹음 없이 개성 있는 목소리를 만드는 합성 방식과 그 음질 검증.
4. 실제 학습된 신경망 가창, 데이터·모델·보코더·네이티브 실행.
5. 세 언어, 여러 표현 방식, 두 플랫폼과 9개 DAW/형식 조합.
6. 권리 자료, 독립 평가, 서명·설치·복원·장시간 동작과 출시 승인.

이는 사용자가 승인한 범위이며 임의로 삭제할 수 없다. 다만 이 모든 것을 하나의 자동 개발 goal의 종료 조건으로 두면, 사람·자료·장비가 필요한 항목 때문에 최종 종료가 불가능한 동안에도 코딩 가능한 주변 작업은 계속 생긴다. **최종 출시 조건이 매일의 작업 선택 기준을 대신하게 된 것이 문제다.**

README는 이미 macOS 가수 작업을 우선하고 Windows를 TODO로 보존하라고 명시한다. Windows가 없어서 전체 Beta GO를 못 하는 것과, 지금 macOS에서 좋은 곡 작업 경험을 만들지 못하는 것은 분리해서 판단해야 한다. Windows 대기는 후자의 변명이 될 수 없다. [S3], [S6], [S10]

## 5. 코드 구조: 유지할 기반과 비용이 큰 경계

**전면 재작성을 권하지 않는다.** 악보의 의도, 합성, 렌더링, 편집 세션, 배포 자원을 나누는 기반이 있고, 기존 테스트는 설치된 가수 선택부터 실제 편집·undo·저장·재열기·출력까지 연결된 경로를 사용한다. 일곱 개의 원곡 작업 테스트는 단순 타입 검사나 가짜 PASS만으로 구성돼 있지 않다. 이를 버리고 새 틀을 만들 근거는 없다. [S11]

반면 다음 변경 비용은 실제로 보인다.

| 관찰 | 의미 | 권고 |
|---|---|---|
| `libs/` 아래 라이브러리 디렉터리 25개. `seam_rendering`은 배포·음성 설계·여러 합성 계층을 함께 참조한다. | 렌더 소스 신원 같은 횡단 문제를 고치면 여러 소비 경로를 확인해야 한다. 모듈 수만으로 나쁜 구조라고 단정하지 않는다. | 다음 실제 사용 결함과 관련된 경계만 개선한다. 모듈 재배치 자체를 목표로 삼지 않는다. |
| native UI도 제작·배포·플랫폼·편집 계층에 넓게 의존한다. `sing_shell.cpp` 5,842줄, `editor_controller.cpp` 4,117줄이다. | UI 변경과 상태 흐름을 이해하는 비용이 크다. 줄 수는 결함 수의 증거는 아니다. | 막힌 사용자 행동을 고칠 때 상태 소유권과 변경 경로를 함께 줄인다. 대규모 분할부터 시작하지 않는다. |
| 저장된 자원 선택과 실제 렌더 소스의 일치 검사가 최근에 보강됐다. | 계약이 여러 층을 통과하면서 일부 의미가 뒤늦게 연결됐다는 구체적 사례다. | 같은 의미의 검사를 CLI마다 다시 만들기보다 제품 경로의 공통 경계를 재사용한다. |
| 검증 후 버렸던 프로젝트를 다시 열지 않도록 `CapturedProjectBinding`이 추가됐다. | 확인한 입력과 실행 입력을 연결하는 개선이다. 기존의 기록 생성만으로 실행을 증명할 수 없었다. | 실제 사용자 출력에 연결될 범위까지 한 작업의 끝을 명확히 정한다. |
| CMake가 HEAD 변경을 감지해 공통 버전 헤더를 갱신한다. | 문서 커밋 뒤에도 재구성·일부 재빌드가 생길 수 있다. 반복 검증 시 실행 파일 정체성도 바뀔 수 있다. | 향후 변경할 때 개발 빌드와 정식 후보의 식별 방식을 검토한다. 출시 정체성을 약화하거나 지금 빌드 체계를 재작성할 사유는 아니다. |

근거는 현재 CMake 의존 관계, 공유 렌더 바인딩 검사, 프로젝트 캡처 타입과 관련 커밋이다. 정적 의존 관계와 파일 크기를 보았을 뿐 전체 의존 그래프나 변경 전파 시간을 계측한 것은 아니다. “구조를 고치면 몇 배 빨라진다”는 수치는 제시할 수 없다. [S9], [S12], [S13], [S14]

## 6. 검증 비용은 실제로 크지만, 모두 낭비인 것은 아니다

기존 `validation-results.json`의 각 명령 시작·종료 시각을 계산했다. 코딩, 리뷰, 공유 머신 차례 대기, 다른 실패·재시도는 아래 합계에 포함하지 않았다.

| 작업 | 빌드 합계 | 테스트 합계 | 명령 실행 합계 | 검증 내용 |
|---|---:|---:|---:|---|
| 상대 경로 자원 승인 수정, `c5769b57` | 8.26분 | 19.87분 | **28.13분** | 전체 Release 237/237, 관련 ASan/UBSan·TSan |
| 프로젝트 캡처 보존, `ecb03168`의 검증 기록 | 0.77분 | 6.03분 | **6.80분** | CLI 관련 23개 native case, source closure, 관련 sanitizer 구성 |

첫 작업의 Release 테스트만 844.21초였다. 별도 원곡 작업 TSan 측정은 7개 사례에 955.44초가 걸렸다. 이 수치는 작은 수정도 여러 검증 구성을 거치면 적지 않은 벽시계 시간을 쓴다는 증거다. **두 표본으로 프로젝트 전체 시간의 몇 %가 검증이라고 추정해서는 안 된다.** 이전 병렬 실행과 이번 직렬 실행의 시간을 비교해 제품이 느려졌다고 결론 내릴 수도 없다. [S15], [S16], [S17]

검증 자체도 정비가 필요했다. 기록에는 오래된 바이너리로 인한 오판, 비동기 대기 시간 초과를 의도된 거부와 혼동하는 테스트, 무결성 불일치를 발견하고도 성공할 수 있었던 검사, 일부 자식 프로세스 진단을 잃는 도우미의 한계가 있다. 이는 “정확성에 집착해서 괜히 생긴 일”로 치부할 수 없다. 신뢰할 수 없는 테스트를 계속 돌려 초록색 결과를 늘리는 편이 더 위험하다. [S1], [S17], [S18]

그렇지만 다음 둘은 구분해야 한다.

- **꼭 해야 하는 검증:** 파일 손실·잘못된 프로젝트 복원, 틀린 가수 또는 이전 오디오의 출력, 자원 승인 우회, 메모리·동시성 오류, 실제 바뀐 경계의 회귀.
- **실행 시점을 선택할 수 있는 검증:** 저위험 문서 수정 뒤의 무관한 전체 행렬, 변경 없는 결과의 반복 수집, 초기 음질 탐색보다 먼저 완성하려는 모든 출시 증거 형식. 원래 필수인 최종 후보 검증은 남겨 둔다.

기존 10월 계획도 이미 “작업 단위별 집중 검사, 통합 지점의 넓은 검사, 이유 없는 전체 반복 금지”를 요구한다. 따라서 새 테스트 정책 문서를 더 만드는 것보다 현재 규칙이 작업 선택에서 실제로 지켜지는지 봐야 한다. 공유 Mac의 검증 잠금은 경쟁 부하를 줄이기 위한 합리적 조치였지만, 대기 중 더 많은 정합성 작업을 만들어 내는 방식은 제품 판단을 앞당기지 않는다. [S6], [S17]

## 7. ‘틀리면 안 된다’는 기준을 어디에 적용해야 하는가

| 구분 | 예 | 지금 필요한 태도 |
|---|---|---|
| 결정적으로 틀리면 안 되는 동작 | 저장한 곡 손실, 다른 가수로 조용히 대체, undo 훼손, 오래된 오디오 출력, 위험한 자원 읽기 | 명확한 불변 조건과 실패 재현, 집중 회귀 검사를 유지한다. |
| 아직 답을 찾아야 하는 음악적 질문 | 원하는 음색인가, 가사가 들리는가, 표현이 유용한가, 수정해서 좋아지는가 | 짧고 재현 가능한 음원과 실제 사용으로 빨리 판단한다. 가설이 틀리는 것은 학습 결과다. |
| 외부 출시를 승인하는 질문 | 권리·독립 평가·서명·실제 Windows/DAW·복원 가능한 증거 | 해당 자료와 권한이 있을 때 정식으로 입증한다. 로컬 초기 탐색의 선행 조건으로 전부 끌어오지 않는다. |

SEAM은 첫째와 셋째에 필요한 엄격함을 많이 구축했다. 지금 부족한 것은 둘째 질문의 답이 첫째·셋째의 작업 순서를 바꾸는 연결이다. **제품을 신뢰할 수 있게 만드는 일과, 만들 가치가 있는 소리·작업 방식을 확인하는 일은 모두 필요하지만 같은 실험으로 해결되지 않는다.**

음원이 생성되고 파일이 존재한다고 사람이 좋아한다는 뜻은 아니다. 반대로 최종 출시 자격이 없는 개발용 가수라도, 명확히 개발용이라고 밝히고 사용자가 방향을 살펴보는 데에는 쓸 수 있다. 다만 그것을 샘플 보이스뱅크가 필요한 정식 Alpha의 대체 증거로 기록해서는 안 된다.

## 8. 음악 엔진의 근본 한계가 있을 가능성

가장 큰 미해결 제품 위험은 **현재 합성 경로가 사용자가 원하는 가수 정체성·발음·표현 품질에 도달할 수 있는가**다. 이것은 설치 검증이나 증거 스키마를 완성해도 해결되지 않는다.

실험용 음원과 원곡 작업 테스트는 존재한다. 10월 4일 packet 001 요약에는 약 199.5초 분량의 음원이 기록되어 있지만 상태는 `RENDERED_UNREVIEWED`, `NOT_REVIEWED`다. 10월 9일 packet 003은 Q1이 요구하는 현상을 선택한 생성 경로에서 입증하지 못해 정식 패킷이 완성되지 않았다. 후자는 합성 엔진 전체 실패가 아니라 **검사하려는 질문과 관찰 경로가 맞지 않은 문제**로 기록돼 있다. [S7], [S19]

현재 신경망 관련 코드·학습 검사는 존재하며, 최근 의존성이 갖춰진 환경에서 469개 학습 관련 검사가 실행된 기록도 있다. 따라서 “신경망은 아무것도 없다”는 주장은 틀리다. 다만 그 기록을 자격을 갖춘 학습 가수의 낯선 노래 품질로 바꿔 읽을 수는 없다. 정식 리소스와 평가 상태는 여전히 별도다. [S3], [S18]

필요한 판단은 다음처럼 갈린다.

| 직접 확인한 결과 | 다음에 할 일 |
|---|---|
| 기본 목소리는 쓸 만하고 특정 음절·전환만 나쁘다 | 그 구간을 재현하고 타이밍·선택·접합·발음 중 지배적인 원인 하나를 고친다. |
| 대부분의 낯선 가사가 알아듣기 어렵고 수정해도 나아지지 않는다 | 자원·발음·합성 방식의 타당성을 먼저 실험한다. 표현 기능과 배포 증거를 더 늘리는 일을 우선하지 않는다. |
| 소리는 충분하지만 작업 도중 계속 길을 잃거나 개발자의 개입이 필요하다 | macOS 작업 흐름, 오류 복구, 선택·편집·저장·출력을 먼저 다듬는다. |
| 소리는 의도대로지만 원하는 제품의 성격과 다르다 | 사용자가 원하는 자연스러움·캐릭터성·거친 합성 질감의 기준을 다시 정한다. 그 뒤 기술 선택을 판단한다. |

이 표는 실험의 해석 규칙이다. 이번 조사에서 실제로 들은 결과를 대신하지 않는다.

## 9. 문서와 리뷰가 많아진 것도 운영 비용이다

`docs/`에는 추적 파일 976개가 있고, 단일 구현 장부는 8,707줄·1,515,516바이트다. 모두 불필요하다는 뜻은 아니다. 다만 현재 상태를 찾으려면 여러 시점의 “다음 작업”과 미완료 문장을 대조해야 하는 구조다. 계약의 `semanticValidation=UNAVAILABLE`와 실제 존재하는 검증 코드처럼 상태 문구가 뒤처진 사례도 있다. 이 환경에서는 인수인계 때 이미 끝난 일을 다시 조사하거나, 오래된 미완료 설명을 현재 결함으로 오인하기 쉽다. [S1], [S3], [S20]

독립 리뷰는 실제 오류를 발견했다. 최근 리뷰는 TSan 판단 기준의 기록 시각에 대한 잘못된 주장을 바로잡았다. 동시에 요청 실패·중단으로 최종 판정이 남지 않은 작업도 있다. 모든 작은 문구·타임스탬프를 실시간 대화로 검토하는 비용과, 음질·사용성 판단을 얻는 비용을 함께 봐야 한다.

이번에는 **Review in English**의 기존 완료 리뷰와 마지막 중단 상태를 읽었다. 현재 세션 간 발신 금지 지침에 따라 새 메시지는 보내지 않았다. 따라서 이 진단 문서에 대해 새 공동 토론이나 독립 승인을 받았다고 주장하지 않는다. [S21]

권고는 문서 삭제나 또 다른 종합 장부가 아니다. 기존 장부를 증거 저장소로 보존하면서, 매 작업의 맨 앞에서 **“사용자의 어떤 행동이 달라지는가 / 무엇을 관찰하면 끝인가 / 이번에 무엇을 하지 않는가”**만 분명히 하고 그 기준으로 다음 일을 고르는 것이다.

## 10. 사용자가 직접 볼 때의 45~60분 가이드

이 세션의 목적은 정식 Beta·Alpha 합격이 아니라 **어떤 개발을 계속해야 하는지 결정할 관찰**이다. 정식 UA에는 샘플 기반 오디오, 30분 안정성, 정량 목표 등 별도 요구가 있으므로 이 짧은 확인만으로 승격하지 않는다.

현재 로컬에는 [Project SEAM.app](</Users/lhs/Downloads/project-seam-usable-alpha-u3-master/build/release/Project SEAM.app>)과 [SEAM Voicebank Studio.app](</Users/lhs/Downloads/project-seam-usable-alpha-u3-master/build/release/SEAM Voicebank Studio.app>)가 존재한다. 이번에는 존재만 확인했으며 해당 앱을 실행하거나 최신 HEAD와의 빌드 일치를 새로 검증하지 않았다. 직접 확인을 시작할 때는 실행 파일·자원·프로젝트를 하나의 명시된 세트로 정해야 한다.

**개발자가 먼저 준비할 것:** 실행 가능한 앱 두 개, 선택할 수 있는 개발용 가수 한 개의 정확한 이름·버전, 새로 입력할 30초 가사/멜로디, 비교용 원본 프로젝트, 빈 출력 폴더. 자원이 없어서 시작할 수 없으면 그것 자체를 첫 번째 방해 요인으로 기록한다. 자동으로 소리 나는 다른 자원으로 바꿔 놓고 성공이라고 하지 않는다.

| 순서 | 사용자가 해 볼 일 | 결정에 필요한 관찰 |
|---|---|---|
| 0~5분 | 앱을 열고 가수를 골라 프로젝트를 만든다. | 무엇을 선택해야 하는지 이해되는가? 터미널이나 개발자 설명 없이는 못 넘어가는 지점은 어디인가? |
| 5~15분 | 처음 보는 짧은 가사와 멜로디를 넣고 듣는다. | 가사가 들리는가? 목소리의 성격이 원하는 방향인가? 첫 번째로 거슬리는 위치를 시각/음절로 남긴다. |
| 15~25분 | 문제 구간의 음높이·타이밍 또는 적용 가능한 표현 하나를 고친다. | 화면의 변경이 소리로 들리는가? 좋아지는가? undo로 돌아오는가? |
| 25~35분 | 가수의 음색을 조금 바꾸거나 초안을 만들어 비교한다. | 목소리를 만드는 기능이 실제로 이해되고 유용한가? 기존 설치 가수·곡은 보존되는가? |
| 35~45분 | 저장하고 종료한 뒤 다시 열어 master/stem을 출력하고 외부 플레이어에서 듣는다. | 재열기 결과와 출력이 작업 중 들은 내용에 대응하는가? 문제가 생겨도 원인을 찾고 복구할 수 있는가? |
| 45~60분 | 가장 큰 문제 세 개와 가장 중요한 제품 기준을 정한다. | 다음 작업 하나를 선택한다. 나머지는 순위를 매겨 보존한다. |

개발자는 사용자의 조작을 대신 성공시키기보다, 도움을 준 순간과 그 이유를 기록해야 한다. 실제 프로젝트에는 강제 종료·자원 삭제 같은 파괴적 시험을 섞지 않는다. 복구·누락 자원 실험이 필요하면 복사본을 별도 세션에서 사용한다.

관찰은 다음 다섯 항목이면 충분하다: **하려던 일 / 기대한 결과 / 실제 결과 / 위치 또는 재현 순서 / 얼마나 작업을 막았는가.** 막히지 않았으면 “지원 없이 성공”, 도움을 받았으면 “도움 필요”, 못 했으면 “막힘”, 해 보지 않았으면 “미확인”으로 남긴다. 이를 임의의 전체 완성도 %로 환산하지 않는다.

## 11. 직접 본 뒤 재개할 때 바꿔야 할 운영 방식

1. **한 번에 하나의 사용자 결과를 끝낸다.** 예: “이 30초 곡의 특정 발음을 고치고 재열기·출력까지 확인한다.” 작은 커밋 원칙은 유지하되, 여러 작은 커밋이 어떤 사용자 결과를 완성하는지 명확히 한다.
2. **다음 수정은 관찰된 가장 큰 문제에서 고른다.** 예외는 실제 데이터 손실·보안·동시성 결함처럼 그대로 진행하면 해를 만드는 문제다. 단순히 쉽게 자동 검증할 수 있다는 이유로 증거 도구를 우선하지 않는다.
3. **통과 기준과 작업 경계를 시작 전에 적는다.** 한 사용 문제를 고치다 추가 경계가 연속해서 나오면 새 하위 시스템을 계속 확장하지 말고, 원래 결과에 반드시 필요한지 판단한다.
4. **검증을 변경 위험에 맞춘다.** 바뀐 제품 경로와 회귀를 먼저 확인하고, 공용 라이브러리는 종속 타깃을 재빌드한다. 넓은 검사·sanitizer·정식 후보 검사는 승인된 의무와 실제 위험에 맞는 통합 지점에서 수행한다.
5. **사람·자료·장비가 필요한 작업에는 구체적인 입력 요청을 둔다.** “청취 필요”라는 문장만 남기지 않고 재생할 파일, 답할 질문, 그 답이 바꿀 개발 결정을 준비한다. 응답이 없다고 관련 없는 기반 작업을 무한히 늘리지 않는다.
6. **보고는 결과와 비용으로 한다.** 새로 가능해진 사용자 행동, 아직 가장 큰 불확실성, 빌드/테스트·대기 시간, 다음 의사결정 하나를 말한다. 커밋·테스트·문서 개수는 보조 정보다.

현재 전체 범위를 줄일지, 최종 Beta를 유지하면서 macOS 중간 결과를 먼저 완성할지, 음질 타당성 연구를 우선할지는 사용자의 제품 확인 뒤 결정해야 한다. **이 문서는 범위를 자동 변경하거나 새 개발 goal을 시작하지 않는다.**

## 12. 이번 작업의 보존 상태와 남은 판단

분석 중 구현을 진행하지 않았다. 기존 미완료 수정 두 파일을 보존했다.

- `apps/seam-voicebank-cli/candidate_package_commands.cpp`: 설치된 recipe와 프로젝트를 실제 export 관찰로 연결하는 진행 중 코드.
- `tests/test_sample_review_cli.cpp`: 위 코드의 진행 중 검사.

두 파일은 합계 206줄 추가·6줄 삭제 상태이며, **컴파일·실행 검증 전**이다. 완료 기능이나 최신 실행 앱의 동작으로 계산하지 않았다. 이 진단을 이유로 해당 코드를 폐기하거나 강제로 통합하지 않았다. 실행 계획·정식 장부·`.github`·Windows TODO·기존 stash도 바꾸지 않았다.

재개 전에 필요한 결정은 거대한 새 계획의 승인이 아니다. **사용자가 원하는 목소리와 노래 작업이 현재 결과에서 얼마나 보이는지 직접 확인하고, 가장 큰 차이가 음질인지 사용 흐름인지 정하는 것**이다. 그 답이 나오면 기존 기반을 활용해 좁게 고칠지, 합성·자원 연구를 먼저 할지 판단할 수 있다. 답이 없는 채로 정합성 작업만 계속하면 지금의 지연 패턴이 반복될 가능성이 높다.
